# PBI portal setup and test guide

This first build accepts **labeled demo projects only**. It never sends a production signing request or creates a live Stripe charge. Do not import real client information into the demo database. The portal lives at `/portal` on its configured host and is excluded from indexing. The public site includes a Clients explanation page and navigation link.

## Local development

1. Check out `beta`, run `npm install`, then `npm run dev`. Open `http://localhost:3000/clients` (or the port shown by Next.js). The public navigation and footer link to this explanation page, not the private workspace.
2. With Clerk keys omitted, open **Client sign in** and select **Owner** to seed GoToHearing and a second isolated demo client. Switch among Owner, Client A, and Client B from the client home or portal page. These are **simulated local identities**, not authentication. Direct public visits to `/sign-up` return to `/clients`.
3. As Owner, edit the project using the normal form or paste a complete object following `example-project.json`. Saving validates required scope, dates, signer fields, and fixed-fee payment totals. Draft data is editable; each generated PDF is a fixed revision.
4. Generate a proposal or agreement, download the PDF, and approve the reviewed revision. For an agreement, start signing. Without Dropbox Sign credentials, the portal creates a visibly simulated request; Client A can simulate completion. This produces **no signature or completed PDF**. Void the request before creating another agreement revision.
5. Create an invoice, approve it, and use the localhost simulation controls to move through initiated, confirmed, or failed states. Its real payment status remains `open`; **no charge occurs**. With a Stripe `sk_test_` key configured, use Stripe-hosted Checkout instead.
6. Run `npm run lint`, `npm run typecheck`, `npm test`, and `npm run build`. `npx tsx tests/portal-pdf-qa.ts` writes ignored QA PDFs under `.data/pdf-qa` for visual review.

The local SQLite database and QA PDFs are under the ignored `.data/` directory. Delete that directory only when you intentionally want to reset all local demo records.

## Private beta configuration

Set the variable names documented in `.env.example` in the beta deployment. Do not commit values. Use a remote libSQL database; Vercel's filesystem is not persistent. Configure Clerk for `beta.piercebusinessintegrations.com`, then sign in as the owner. Copy the verified Clerk user ID and run `PORTAL_ADMIN_USER_ID=... npm run portal:admin` with the remote database URL/token in the shell environment. The script grants that identity the server-side owner role. In PowerShell, assign environment variables with `$env:PORTAL_ADMIN_USER_ID = 'user_...'` and run the command in the same session. Clear the temporary variable afterward.

The public `/clients` page explains access and links to `/sign-in`. `/account`, `/account/profile`, and `/portal` are for authenticated identities with a portal membership; users without one cannot enter the workspace or call its project APIs. `/sign-up` renders Clerk's onboarding UI only when an invitation ticket reaches that URL; a direct visit returns to `/clients`. In the Clerk Dashboard, set **Access mode → Invite-only** before beta use. This provider setting is essential: the site cannot restrict account creation inside Clerk by hiding a link. Create client invitations in Clerk, verify the identity, then assign the corresponding Clerk user ID to the correct PBI organization. Configure the sign-in and invitation URLs from `.env.example` and test an actual invite before beta launch. [Clerk's access-mode guide](https://clerk.com/docs/guides/secure/restricting-access) describes Invite-only behavior.

## Client subdomain

The production client entry is `https://client.piercebusinessintegrations.com`. It runs the **same Next.js deployment** as the marketing site; `/` on that host redirects to `/portal`. Production requests for `/portal`, `/account`, `/sign-in`, and `/sign-up` on the primary or old PWS domains permanently redirect to the client host, retaining paths and query strings. On the client host, the listed marketing pages redirect to the primary site. The public `/clients` page links directly to the client sign-in in the production build. Localhost and `beta.piercebusinessintegrations.com` keep their existing same-host portal paths for testing.

Before sending a client this URL, add `client.piercebusinessintegrations.com` to the **same Vercel project** as the main site, inspect the domain in Vercel, create the exact CNAME record Vercel requests at the DNS provider, and verify HTTPS and the `/` → `/portal` redirect. Do not guess a universal CNAME target; Vercel may provide a project-specific value. The repository has no linked `.vercel` project or Vercel CLI credentials, so domain attachment and DNS have not been performed. [Vercel custom-domain setup](https://vercel.com/docs/domains/set-up-custom-domain) covers the external steps.

Configure Clerk's production root domain and allowlist the `client` subdomain; keep beta in the allowlist only if it uses the same Clerk instance. `PORTAL_AUTHORIZED_ORIGINS` can override the code's production `https://client.piercebusinessintegrations.com` and preview `https://beta.piercebusinessintegrations.com` defaults when a deployment has a different hostname. Confirm the sign-in, invited sign-up, Google OAuth callback, and post-login return on the client host in a regular browser. Clerk shares sessions across subdomains by default; the allowlist and authorized parties reduce unnecessary cross-subdomain exposure. [Clerk subdomain guidance](https://clerk.com/docs/guides/dashboard/dns-domains/subdomain-allowlist) and [production deployment guide](https://clerk.com/docs/guides/development/deployment/production) explain these settings.

For production provider setup, use `https://client.piercebusinessintegrations.com/api/portal/webhooks/dropbox-sign` and `https://client.piercebusinessintegrations.com/api/portal/webhooks/stripe`. Keep the beta callback URLs below for sandbox testing. Stripe Checkout return URLs are derived from the host that starts checkout; verify they return to the client host in a provider test. No domain, provider, or production deployment change is part of this local build.

If Google is enabled for invited clients, configure it in the Clerk Dashboard. A development Clerk instance can use its shared Google OAuth configuration; a production instance needs a Google OAuth client and the exact authorized redirect URI shown by Clerk. Test Google in a regular browser: Google may reject OAuth inside embedded WebViews, including some in-app browsers. See [Clerk's Google setup guide](https://clerk.com/docs/guides/configure/auth-strategies/social-connections/google).

The owner may grant a verified Clerk client user ID access to one organization from its project page. The portal checks membership on every project, document, invoice, signing action, and private PDF download. Do not share a development identity cookie or rely on a hidden URL for access. The beta deployment uses Clerk; the local identity selector is unavailable when `NODE_ENV=production`.

An accepted invitation creates a Clerk identity, **not** project access. The owner must verify the person and grant the correct organization membership. A signed-in identity without membership sees an access message and contact route at `/account`; it cannot enter `/portal` or enumerate client records.

## Signing sandbox

Create a Dropbox Sign API app and configure its app callback URL to `https://beta.piercebusinessintegrations.com/api/portal/webhooks/dropbox-sign`. Set `DROPBOX_SIGN_API_KEY`, `DROPBOX_SIGN_CLIENT_ID`, and the verified PBI signer mailbox/name. The adapter forces `test_mode=1` and uses embedded signing. The client must be assigned portal membership and have a Clerk email matching an agreement recipient. The callback verifies Dropbox Sign's event HMAC, records duplicate events once, and downloads the completed PDF when the downloadable event arrives. The downloaded PDF includes the provider audit trail. The owner must visually confirm signing field placement and test the full provider flow before treating this integration as working. Dropbox Sign production API-plan cost and legal clauses remain unapproved.

## Stripe test checkout

Use only an `sk_test_` secret key. Configure a Stripe test webhook endpoint at `https://beta.piercebusinessintegrations.com/api/portal/webhooks/stripe` and listen for `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, and `charge.refunded`. Set its `whsec_` signing secret. Stripe Checkout hosts card/bank collection. Enable `STRIPE_ENABLE_ACH=true` only if US bank account payments are available in the test account. A checkout return does not mark an invoice paid; verified events do. Processing remains separate from paid. The invoice's amount, currency, document revision, and Stripe session must match before a payment event updates status. Stripe Invoicing is not used.

## Current limits

No Clerk, Dropbox Sign, remote libSQL, or Stripe account credentials were available for this build, so those external paths have **not** been exercised. Local identity, signing completion, and payment states are simulations with separate labels/columns; they are not evidence of real authentication, a legal signature, or payment. No production deployment, invitations, real agreements, or real charges have been made. The terms in the demo fixture are unreviewed placeholders. Review provider costs and legal text before real use.
