## Decisions

- Keep the existing marketing site and its Next.js architecture.
- Use Supabase Postgres in a private, unexposed `pbi_portal` schema; explicit checked-in migration, no hosted runtime DDL. Server queries retain existing membership checks and atomic billing/stage updates. Browser roles cannot read/write portal tables; RLS denies direct API access. The privileged database URL stays server-only, uses the Supabase transaction pooler, and verifies TLS. An ignored SQLite file remains local-preview-only.
- Use Supabase Auth with server-confirmed identity, PKCE Google sign-in, existing-user email OTP/password sign-in, host-only HttpOnly cookies, and session refresh. Disable provider public signups/anonymous sign-ins. Membership is server role data, never editable profile metadata. Owner tools connect existing users by email or generate one-time invitation links without emailing them. Explicit POST acceptance protects invitations from link scanners.
- Store hosted PDFs in the private Supabase Storage bucket and serve them through authorized no-store routes with checksum verification. Storage bytes need separate backup from database backups. Local preview PDFs remain SQLite blobs.
- Use deterministic PDF templates built from validated structured data. No AI API is required. The agreement clause set is unreviewed demo text until approved by counsel.
- Use SignWell embedded signing with ordered recipients and test mode by default. Live capability requires the explicit hosted-client gates added October 4; no live request was issued. Generated v3 agreement PDFs record exact signer-field geometry, including the pixel-scale conversion. Existing PDF revisions stay intact; v2 agreements need a new revision before SignWell. Provider state is rechecked before issuing a signer URL or marking completion.
- Persist verified SignWell events before acknowledging callbacks. Process after the response, save the completed PDF/audit page privately, and retain failed work for explicit retry. Duplicate/late events cannot rewrite completed originals. Schedule retry/monitoring before external rollout; the retry command is implemented, no hosted schedule is deployed.
- Use Stripe hosted Checkout in explicitly configured provider mode, test by default. A return page is informational; only verified webhooks change payment status.
- Store an ordered, owner-managed stage plan separately from invoices and editable scope. Work progress never follows payment state automatically. Each stage can have one active invoice, and invoicing remains an explicit owner action tied to the agreed payment schedule.
